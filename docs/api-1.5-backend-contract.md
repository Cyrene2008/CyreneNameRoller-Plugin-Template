# Plugin API 1.5 Backend Contract

> **未启用 / migration-only**：本页记录 API 1.5 契约。当前仓库的启用路径是 API 1.4 + `manifest.yml` + `contributions.json`（见仓库 README）。API 1.5 材料仅供迁移参考，默认的 validate / build / test 不使用它们。

This document describes the host contract behind the public API 1.5 SDK. It
is an implementation reference for the CyreneNameRoller host and SDK authors.
Plugin code must use the SDK groups rather than calling native commands or
constructing RPC envelopes directly.

## Contract boundaries

There are four layers:

| Layer | Consumer | Status |
| --- | --- | --- |
| SDK groups | Plugin Worker and declared plugin pages | Public API |
| API 1.5 JSON-RPC | Host runtime and bundled runner | Versioned transport contract |
| Core Worker messages | Host Web runtime only | Internal; never exposed to plugins |
| Tauri commands | Host frontend/native bridge only | Internal; never exposed to plugins |

The host owns plugin processes, Workers, WebViews, routes, windows, styles,
DOM handles, broker requests, core state, and audit records. A plugin receives
opaque IDs and structured snapshots, never native handles, Pinia stores, Core
Worker ports, Tauri internals, or host object references.

## RPC envelope

Every API 1.5 request, response, event, cancellation, heartbeat, and shutdown
message carries the protocol and negotiated API marker:

```json
{
  "jsonrpc": "2.0",
  "protocol": "cnrp-jsonrpc/1",
  "api": "1.5",
  "kind": "request",
  "id": "req-random-id",
  "pluginId": "cn.example.plugin",
  "instanceId": "instance-random-id",
  "idempotencyKey": "operation-random-id",
  "method": "core.operations.execute",
  "params": {}
}
```

`id` is generated by the host/SDK and must be unique for the session.
`idempotencyKey` is required for operation requests. Retrying an idempotent
request with the same key replays the stored response. A non-idempotent
request must use a fresh key. `pluginId` and `instanceId` are checked against
the authenticated session on every message.

The desktop transport uses one little-endian length-prefixed UTF-8 frame:

```text
4-byte unsigned payload length + UTF-8 JSON payload
```

The maximum frame is 1 MiB. Binary data is represented by base64 chunks, each
at most 256 KiB, with validated `chunkIndex`, `chunkCount`, and total operation
size. A binary operation is limited to 32 MiB. Raw `Uint8Array` values are not
valid JSON-RPC payloads.

## Session lifecycle

The authenticated desktop lifecycle is:

```text
host hello
  -> plugin hello.accepted
host initialize(granted capabilities)
  -> plugin ready
      request/response/event traffic
host shutdown
```

The host supplies normalized metadata and resolved capabilities only. Session
credentials travel through the private inherited channel or the bounded
credential prelude used by the native fallback. Credentials are never placed
in argv or a broadly visible environment variable. A credential proof is
bound to the plugin ID and instance ID.

Web plugins use the same logical lifecycle over `Worker.postMessage()` and
structured cloning. Required unavailable capabilities block activation;
optional unavailable capabilities stay discoverable and return
`UNSUPPORTED_PLATFORM`.

## Page state

`page.read` accepts `{ "field": string }`. `page.write` accepts a single
canonical field and value. Ordinary writable fields are:

```text
language
theme
animation
display
roller.filters.listId
roller.filters.target
roller.filters.count
roller.filters.gender
roller.filters.allowDuplicates
```

The host validates type and bounds, applies the corresponding host action, and
persists ordinary settings. Sensitive fields require a confirmation ID bound
to the exact proposed patch:

```json
{
  "patch": { "field": "permissions", "value": {} },
  "confirmationId": "host-confirmation-id"
}
```

Sensitive categories include plugin enablement, permissions, list contents,
import/export, record clearing, fairness settings, and window security.

## Pages, windows, styles, and DOM

Pages are declared in `manifest.pages`; runtime page registration does not
exist. Native routes precede plugin routes, then plugin load order and
manifest declaration order determine the rest. Page IDs, window IDs, style
handles, and node IDs are opaque and plugin-owned.

Initial limits per plugin are:

| Resource | Limit |
| --- | ---: |
| Windows | 4 |
| Pages | 16 |
| Injected style handles | 32 |
| DOM insertions/nodes | 128 nodes per bounded operation |
| Concurrent RPC requests | 32 |

`style:main` and `style:settings` create host-owned style elements. Removal,
abort, disable, crash, unload, and safe mode remove the corresponding handles.

DOM operations accept structured selectors, node IDs, allowlisted fields, and
structured nodes. `insert` creates real host DOM Nodes from tag/text/attribute
data. These are rejected:

- `dom.execute`
- raw HTML or script URLs
- inline event handlers and function source
- host object references
- cross-plugin node IDs
- `window.__TAURI_INTERNALS__` and other host globals

Snapshots are bounded and contain only tag, text, attributes, and child count.

## File broker

File requests use relative paths under a host-owned staged package or an
explicit manifest-declared external root. The native side rechecks session
ownership, canonical roots, file size, regular-file status, and symlink/reparse
components. Traversal, protected core roots, UNC paths, drive-relative paths,
extended Windows aliases, 8.3 aliases, and root escapes are denied.

External execution is not implied by file write access. An executable must be
listed exactly in the manifest declaration and its arguments must pass the
fixed argument policy. Arbitrary shell commands require the separately
explicit `system:execute` risk and still use fixed manifest operations.

## Network broker

Only `http:` and `https:` URLs are accepted. Requests have bounded headers,
body, response size, timeout, and concurrency. Loopback, link-local,
metadata, private, alternate IPv4, IPv4-mapped IPv6, and unresolved addresses
are denied. Redirects are denied unless the host can validate and bind every
target without a DNS-rebinding gap. The current Web implementation fails
closed when browser fetch cannot atomically bind the validated address.

Network responses use bounded body data and report the transferred byte count
in the host-only audit record. Cancellation carries the RPC request ID and
propagates an `AbortSignal` through the broker where the platform supports it.

## Core operations and hooks

Core operation input contains filters only:

```json
{
  "operation": "draw",
  "filters": {
    "listId": "default",
    "target": "people",
    "count": 1,
    "gender": "all",
    "allowDuplicates": false
  }
}
```

The only hook-mutable fields are `listId`, `count`, `gender`, and
`allowDuplicates`. The algorithm, random state, candidate set, results,
records, statistics, prize inventory, and next-state envelope are host/core
owned. The core validates protected state before every operation and commits
atomically through the Web Core Worker or Rust core.

Before hooks execute serially in deterministic plugin load order. A hook
returns either:

```json
{ "decision": "allow", "filters": { "count": 2 } }
```

or:

```json
{ "decision": "abort", "reason": "plugin-defined reason" }
```

The host records original, per-plugin, and final filters in the receipt and
audit trail. The per-hook deadline is at most three seconds and the cumulative
budget is five seconds. Three hook failures in ten minutes or five explicit
aborts in ten minutes automatically disables the plugin. After-operation
events are delivered only after a successful commit.

## Errors and retry behavior

| Error | Meaning | Retry |
| --- | --- | --- |
| `UNSUPPORTED_PLATFORM` | Optional capability unavailable | Use fallback or skip |
| `PERMISSION_DENIED` | Capability not granted | No, request installation change |
| `PENDING_CONFIRMATION` | Host confirmation required | Retry with confirmation ID |
| `RESOURCE_LIMIT` | Per-plugin quota exceeded | Release resources first |
| `PLUGIN_INSTANCE_REVOKED` | Session is stale/disabled | No, reactivate plugin |
| `TIMEOUT` | Request or hook deadline exceeded | Fresh idempotency key if non-idempotent |
| `CANCELLED` | Request was cancelled | Fresh request if appropriate |
| `NETWORK_ADDRESS_DENIED` | Destination is private/unresolved | No without explicit safe host policy |
| `NETWORK_REDIRECT_DENIED` | Redirect violates policy | No |
| `PATH_OUTSIDE_ROOT` | File escapes declared root | No |
| `EXECUTABLE_NOT_DECLARED` | Executable is not fixed in manifest | No |
| `CORE_TRANSACTION_REJECTED` | Invalid core intent/input | Fix input |
| `CORE_TRANSACTION_ROLLED_BACK` | Persistence failed; no commit | Retry after host recovery |
| `CORE_INTEGRITY_FAILURE` | Protected state mismatch | Stop and recover; never retry blindly |

Errors returned as structured capability results contain `ok: false`,
`code`, and a bounded `message`. Host-side exceptions must not expose paths,
credentials, stack traces, or native handles to plugin code.

## Audit and cleanup

The host audit record is append-only and inaccessible to plugins:

```json
{
  "time": "2026-01-01T00:00:00.000Z",
  "pluginId": "cn.example.plugin",
  "instanceId": "instance-id",
  "method": "net.request",
  "resource": "example.com",
  "decision": "allow",
  "resultCode": "OK",
  "bytes": 128,
  "durationMs": 42,
  "correlationId": "correlation-id"
}
```

Network resources are reduced to hostnames. Local paths are reduced to safe
host identifiers. Denials, failures, cancellations, timeouts, and successful
requests are audited. Retention is bounded by record count and total storage
size; cleanup removes all session-owned processes, routes, hooks, styles,
DOM contributions, windows, requests, and opaque IDs.

## Internal native commands

Commands such as `plugin_runner_start`, `plugin_runner_send`,
`plugin_files_read`, `plugin_net_request`, and `core_prize_execute` are
internal Tauri implementation details. They are not part of the plugin API and
must not be invoked directly by plugin code. The frontend host supplies the
authenticated session identity and manifest-derived grants before using them.
